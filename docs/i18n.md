# Translations (i18n)

CommerceOS uses **i18next** (with react-i18next), the standard React
translation stack. Texts live in plain JSON files, one per language and
namespace, which translation platforms (Crowdin, Lokalise, Weblate, …) read
and write directly.

| App | Files | Language comes from |
|---|---|---|
| Storefront (shopper texts) | `storefront/src/i18n/locales/<lang>/shop.json` | the page URL: the channel's **Storefront language** (`storefront_locale`) under the plain store path, every other offered language (`storefront_locales`) under `/store/{key}/{lang}/…` |
| Theme editor (merchant texts: toolbar, inspector, component names and settings) | `storefront/src/i18n/locales/<lang>/editor.json` | the admin user's language, carried by the edit session (the editor draft's `locale`); the canvas still previews in the store's language |
| Admin (every screen) | `frontend/src/i18n/locales/<lang>/<module>.json` (one namespace per module, loaded automatically) | the user's pick in the top bar, kept in the `cos_lang` cookie; without one, the company language (Settings → Localization; the browser language until it loads) |
| Shopper texts the backend writes (sign-in link and newsletter confirmation emails, the payment-page description) | `backend/application/shopperemail/locales/<lang>.json` | the channel's Storefront language |
| Theme preset content (a new theme's headings, banners, menus) | `backend/domain/theme/presettext/<lang>.json` -- English text → translation (gettext style); presets are written in English | the channel's Storefront language when the theme is created |

| Notifications (bell + notification emails) | admin `frontend/src/i18n/locales/<lang>/notifications.json` (bell) and `backend/domain/notifications/texts.go` (emails) -- kept word for word equal by `TestTypeTexts_matchTheAdminTranslations` | bell: the admin user's language; email: the company language |
| API error messages | admin `frontend/src/i18n/locales/<lang>/errors.json`, theme editor `storefront/.../editor.json` (`errors.*`), storefront `shop.json` (`errors.*`) -- keyed by the backend's error codes (`backend/domain/errs`, `errs.New("CODE", "english")`); `TestEveryErrorCodeIsTranslated` (cmd/api) fails on a code without an admin text | the reader's language |

Languages today: `en` (source), `pt-BR`, `nl`.

## File format

```json
{
  "cart": {
    "empty": "Your cart is empty.",
    "quantityOf": "Quantity of {{name}}",
    "items_one": "{{count}} item",
    "items_other": "{{count}} items"
  },
  "account": { "signInFirst": "Please <link>sign in</link> to see your account." }
}
```

- **Placeholders** are `{{name}}`; keep them exactly as in English.
- **Plurals** use `_one` / `_other` suffixes (plus `_zero`, `_few`, `_many`
  where a language needs them) and are chosen from `count`.
- **Tags** like `<link>…</link>` or `<strong>…</strong>` wrap words that the
  code turns into links or bold text; keep them, move them freely.
- A **blank** text (`""`) falls back to English, so a half-translated
  language still works.

## Everyday tasks

Run these in the app folder (`storefront/` or `frontend/`). The admin also has `npm run i18n:types`
(run after adding a namespace file; `i18n:extract` runs it for you), and a test that fails on
UI text written straight into a component.

**Add or change a text in the code**

1. Use it in code: `const { t } = useTranslation()` then `t('cart.empty')`.
   Keys are typed from the English file, so a typo doesn't compile.
2. `npm run i18n:extract` adds new keys to every language file (English gets
   the key as its text, other languages get `""`) and removes unused ones.
3. Write the English text in `en/shop.json`, translate the others.
4. `npm run i18n:check` lists what's still missing.

Keep code extractable: call `t('literal.key')` with a literal key (the
extractor can't see keys built at runtime and would delete them), use one
primary namespace per file (`useTranslation(['orders', 'common'])`, reach
others as `t('common:actions.save')`), don't nest `t()` inside another
`t()`'s options, and use `{{count}}` only for real plurals (`_one`/`_other`)
-- for a plain number in brackets use another name, e.g. `{{n}}`.

**Fix a translation:** edit the JSON file, run `npm run i18n:check`.

**Component and style texts (editor).** Component names, descriptions,
setting labels and options, and style-control labels are written in English
in the code (`src/components/**` definitions, `src/editor/inspector/styleControls.ts`).
`editor.json` carries a copy under `components.*`, `categories.*` and `style.*`
so translators see them. After changing one in code, run
`npm run i18n:registry` to refresh the English copy (a test fails until
you do), then translate the new texts. Size tokens (`xs`, `2xl`, `16:9`,
`H2` …) are never translated.

**Add a language**

1. `npm run i18n:add de` creates `locales/de/*.json` with blank texts.
2. Translate them (or upload to your translation platform); check with
   `npm run i18n:check`.
3. Register the language:
   - `src/i18n/locale.ts`: add it to `LOCALES`, `LOCALE_NAMES`, `INTL_LOCALE`
   - `src/i18n/resources.ts`: import its files
   - `i18next-parser.config.js`: add it to `locales`
   - backend: `domain/channels/storefront_locale.go`, the `StorefrontLocale`
     enums in `api/integrations/openapi.yaml` and `api/storefront/openapi.yaml`,
     and a migration extending `sales_channels_storefront_locale_check`.
4. The catalog test then requires it to be complete.

A new language also needs a `backend/application/shopperemail/locales/<lang>.json`
(a Go test checks every language has every text with the same placeholders).

## Languages of a store

- **Company language** (Settings → Localization, `tenant_settings.language`):
  the admin language for users without their own pick, and the storefront
  language a new sales channel starts with.
- **Storefront language** (`sales_channels.storefront_locale`): the default,
  served on plain store URLs.
- **Other languages** (`sales_channels.storefront_locales`, the default
  first): each served under its own prefix, e.g. `/store/{key}/nl/products/x`.
  Pages link within their language, carry `hreflang` alternates (+
  `x-default`), and the sitemap lists every version.
- The **language switcher** component (in both presets' headers) links the
  current page in each language and remembers the pick in the per-store
  `cos_shop_lang` cookie; a plain store URL then redirects (302) to it. It
  renders nothing while a store offers one language.

## Merchant texts in several languages

Component texts the merchant writes in the theme editor (headings, rich
text, button labels, menu links, …) can differ per language. The component
settings themselves are the store's default language; with **Texts in**
(editor toolbar, shown once the store offers more than one language) set to
another language, the inspector edits only the texts, into the node's
`translations[<lang>]`. A text left untranslated (or cleared) shows the
default-language text. Layout, pictures and choices are shared by every
language.

Which props are translatable is in the theme contract
(`x-commerceos-component` `translatable`); the storefront derives the same
list from the prop kinds (`text`, `richtext`, `links`) and a contract test
keeps both in step. The backend rejects other props and unsupported
languages, and validates each language's texts like the defaults.

## Catalog texts in several languages

- **Products:** name and description per language (admin product page →
  Translations; `PUT /pms/products/{id}/translations`, kept apart from
  product updates so channel syncs never touch them). Shopper search also
  matches translated names.
- **Collections:** name, description and SEO texts per language, in the
  collection form.
- **Storefront API:** the product and collection endpoints take
  `?locale=`; the storefront sends it on non-default-language pages.
  Untranslated texts come back in the company language.
- **Theme pages:** title and SEO texts per language (editor, "This page").
- Channel syncs (WooCommerce, Bol), cart/order lines, emails and invoices
  keep the company language.

## Not translated (yet)

Backend error messages (shown as-is where the API returns them) are
English.
